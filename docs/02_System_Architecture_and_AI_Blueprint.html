1. Architecture Executive Summary Architecture Decision

The DailyBlog AI System Architecture defines the technical implementation required to fulfill the multi-tenant, human-governed automated content platform specified in Document 1. While Document 1 defines WHAT the product accomplishes across company workflows, Document 2 establishes HOW the system is structured, partitioned, orchestrated, and persisted.

The planned architecture eliminates the fragility of unconstrained scripts by decoupling synchronous web interactions from stateful generative AI loops and asynchronous CMS dispatch pipelines:

FastAPI & Clean Layering

[IMPLEMENTED] High-performance asynchronous REST API built with FastAPI and Pydantic schemas. Strictly separates presentation routing from domain business services and repository query layers. Core routing and dependency injection implemented.

PostgreSQL + pgvector Dual Engine

[IMPLEMENTED / DESIGN] Unifies relational business state (tenants, users, schedules, reviews, audit logs) and dense vector embeddings in a single durable PostgreSQL store with tenant-scoped filtering, avoiding distributed split-brain failure modes.

LangGraph State Machine

[ARCHITECTURE / DESIGN] Stateful graph orchestration coordinating multi-step research, outlining, drafting, SEO validation, and Human-in-the-Loop approval checkpoints with explicit checkpoint persistence. Specified target AI engine.

Redis & Celery Asynchronous Workers

[ARCHITECTURE / DESIGN] Decouples scheduled publishing dispatch, periodic scheduler jobs (Celery Beat), background ingestion/processing where appropriate, and long-running asynchronous tasks from synchronous client HTTP lifecycles, while LangGraph orchestrates the stateful AI workflow and human-in-the-loop state transitions.

2. Architecture Principles Architecture Decision

The planned architecture adheres to eight non-negotiable architectural principles:

Principle Architectural Meaning & Enforcement Failure Mode Prevented
1. Tenant Partitioning Tenant ID (company_id) is injected at authenticated boundaries and enforced across SQL queries, pgvector cosine queries with tenant-scoped filtering, and thread checkpoints. Cross-company data leakage or competitive prompt poisoning.
2. Single Cycle Invariant AT MOST ONE ACTIVE BLOG CYCLE PER COMPANY: Exactly 0 active cycles = valid idle state; exactly 1 active cycle = valid post in progress; 2+ active cycles = strictly invalid and blocked by concurrency controls. This invariant is protected through transactional concurrency enforcement (database transaction isolation, conditional/partial uniqueness enforcement, row-level locking during cycle initiation, and atomic state transitions). A company may have many historical blogs, at most one active blog cycle at any given time, and future recurring schedule definitions. Concurrent draft collisions, race conditions during cycle initiation, or duplicate scheduled publications.
3. Human Editorial Gate Automated publishing cannot occur without explicit Reviewer approval passing time-gated review windows. Unchecked AI hallucinations reaching production company websites.
4. Stateful Thread Continuity The entire lifecycle of a daily blog (topic, draft, revisions, reviewer comments) remains within a single unified conversational thread. Disjointed review context or loss of prompt history during revisions.
5. Separate Memory Planes Short-term ephemeral thread working memory is strictly separated from verified long-term durable company memory. Transient feedback polluting immutable organizational brand guidelines.
6. Headless CMS Isolation External publishing providers (WordPress REST API) are encapsulated behind an abstract adapter interface. Direct coupling to third-party CMS quirks or tight lock-in.
7. Asynchronous Decoupling Asynchronous and scheduled operations (scheduled publishing, periodic scheduler jobs, background ingestion/processing, and long-running background tasks where appropriate) execute in Celery worker queues backed by Redis, while LangGraph orchestrates the stateful AI workflow and human-in-the-loop state transitions. Blocking API threads or HTTP gateway timeouts during background tasks or complex multi-step workflows.
8. Security Defense-in-Depth Passwords hashed with salted algorithms; third-party CMS credentials encrypted at rest; strict rate limits on OTP/CAPTCHA. Credential harvesting, brute-force entry, or token leakage.

8. Knowledge Ingestion & RAG Architecture Architecture Decision

The Retrieval-Augmented Generation (RAG) pipeline ingests reference documents (PDF, DOCX, TXT) and indexes them for precise similarity search:

Visual 3: Asynchronous Knowledge Ingestion & RAG Pipeline

Chunking utilizes a recursive token strategy where chunking parameters are configurable and selected according to document characteristics and the chosen embedding model. Embeddings are generated via a provider-agnostic embedding interface and stored in PostgreSQL using the pgvector extension in a table containing company_id, document_id, content, and embedding vector. Vector similarity queries employ HNSW indexing with tenant-scoped filtering by company_id, ensuring strict tenant isolation during similarity searches. The vector dimension is determined by the selected embedding model and must remain consistent with the configured vector schema/index.

Conceptual Boundary — RAG / Knowledge vs. Memory Systems:

While both RAG knowledge chunks and long-term memory may utilize PostgreSQL and pgvector storage infrastructure, they represent fundamentally distinct conceptual data domains:

  • RAG / Knowledge Base: Ingests external reference documents (PDFs, DOCX, TXT, corporate factsheets, whitepapers) via chunking and vector embeddings to provide factual, source-grounded context retrieval during research and drafting.
  • Memory Subsystem: Manages internal organizational identity and operational context (brand voice guidelines, verified company preferences, historical accepted topics/content patterns, durable organizational preferences, and active conversation thread state).
  • Domain Invariant: Not every vector embedding is "memory," and not every organizational memory item must be a vector embedding. Vector search is an indexing mechanism; memory is durable organizational state and conversational working context.

11.1 AI Prompt Architecture & Prompt Contracts [ARCHITECTURE / DESIGN]

To ensure deterministic, brand-aligned, and hallucination-resistant content generation, the AI orchestration engine assembles prompts from controlled, strictly ordered context layers. Prompts are never raw user queries; they are programmatically synthesized prompt contracts compiled from verified organizational data, retrieved knowledge, and editorial constraints.

Prompt Strategy Principles:
  • Layered Assembly: Prompts are assembled hierarchically from highest-authority system constraints down to task-specific user instructions.
  • Tenant Boundary Grounding: Only company-approved context and tenant-scoped retrieved chunks are injected; no cross-tenant knowledge is ever accessible.
  • Anti-Hallucination Guardrails: The model is explicitly constrained from fabricating unsupported company claims, pricing, or product features.
  • Structured Output Enforcement: All generation nodes require strictly typed Pydantic-compatible JSON or AST-parsable markdown conforming to schema contracts.
Visual 5B: Hierarchical Prompt Context Assembly Architecture

Controlled Context Layers & Architectural Responsibilities

Layer Source & Scope Contents & Injected Attributes Architectural Invariants & Guardrails
1. SYSTEM INSTRUCTIONS Immutable Code Role of the model, task boundaries, structural compliance directives, forbidden behaviors. Absolute authority. Strictly forbids fabricating company facts; forces output to follow typed schemas.
2. COMPANY CONTEXT company_ai_profiles Company identity, industry, offerings, audience personas, brand voice parameters, marketing goals, promotional rules, guidelines, upcoming projects, and partner companies. Tenant-scoped. Injected from verified database records. Must not be mutated by chat prompts.

17. Rescheduling & Active Cycle Invariant Architecture Architecture Decision

Rescheduling provides a controlled, one-time target publishing timestamp override for the currently active article while maintaining continuous workflow state:

  • Separate Review Window vs. Cutoff: The reschedule decision is triggerable by the Reviewer strictly within the 20–10m window before current target publish time. However, the requested new publishing timestamp must be at least one hour before the next scheduled publishing slot (e.g., if next regular slot is Tuesday 4:00 PM, current post can be rescheduled up to Tuesday 3:00 PM).
  • Cycle Preservation: Rescheduling mutates the target publish timestamp (implementation field: blogs.scheduled_at; architecture terminology: target_publish_at). It does NOT spawn a new conversation or archive the current cycle. The same Editor-AI conversation thread continues seamlessly.
  • Active Cycle Invariant (0, 1, or 2+ Invariant Rule): The architecture strictly distinguishes between three independent entity scopes:
    1. Historical Blogs: Any number of previously accepted, rejected, or published blog records preserved durably in PostgreSQL for audit, analytics, and content referencing.
    2. Current Active Blog Cycle: AT MOST ONE ACTIVE BLOG CYCLE PER COMPANY:
      • 0 active cycles = valid (system is idle, between scheduled publication slots).
      • 1 active cycle = valid (a single blog post is actively in ideation, drafting, review, or dispatch).
      • 2+ active cycles = strictly invalid (prevented by strict concurrency controls).
    3. Future Publishing Schedule Definitions: The master recurring weekly timetable (Monday–Sunday) managed by the Reviewer.
  • Transactional Concurrency Enforcement: The at-most-one active cycle invariant is guaranteed through database concurrency controls, including database transaction isolation, conditional/partial uniqueness enforcement (such as a partial index on non-terminal blog statuses per company), row-level locking during cycle initiation, and atomic state transitions. Subsequent daily cycles are blocked from initializing until the current active cycle reaches a terminal resolution (successful publication or explicit rejection).

18. Scheduling & Background Jobs Architecture Decision

Scheduling coordinates the recurring weekly timetable with Celery worker execution:

Visual 9: Scheduling & Celery Beat Execution Architecture

Transactional Scheduler Checks & Active Cycle Invariant

The active cycle invariant (AT MOST ONE ACTIVE BLOG CYCLE PER COMPANY: 0 = valid idle, 1 = valid active, 2+ = invalid) is actively verified before any daily cycle begins. (Field Mapping: Implementation field in blogs table is scheduled_at; architecture documentation refers to this target timestamp as target_publish_at.)

  • Pre-Execution Verification: When the Celery Beat scheduler triggers for a company's scheduled day/time slot, it queries blogs for any article in a non-terminal status (IDEATION, DRAFTING, PENDING_REVIEW, EDITING, NEEDS_IMPROVEMENT, PUBLISHING, or PUBLISHING_UNKNOWN).
  • Conflicting Cycle Rejection: If an active cycle exists, the scheduler logs an ACTIVE_CYCLE_HOLD and suppresses creation of a new cycle. Company A cannot have Cycle 1 active and Cycle 2 accidentally created simultaneously.
  • Concurrency Controls: Enforced through database transaction isolation, server-side validation rules, row-level locking during cycle initiation, and partial unique constraints (e.g. conditional index on active blog statuses per tenant).

Reviewer Ownership vs. Admin/Editor Read-Only

The publishing schedule (Monday–Sunday timetable with 24-hour time and toggle switches) is owned strictly by the Reviewer. Company Admins and Editors possess read-only visibility. Changes made by the Reviewer update the PostgreSQL schedule rows immediately, which Celery Beat inspects dynamically on its 60-second polling cadence.

Fernet-Based Credential Encryption

Publishing credentials (WordPress Application Passwords and target endpoints) are encrypted at rest using application-level Fernet symmetric encryption. The encryption key is supplied through protected environment configuration and is never hardcoded or returned through normal API responses. Plaintext credentials are never exposed across client-facing REST APIs and are decrypted strictly within ephemeral worker memory immediately before dispatch.

Integration Verification Prerequisite Implementation hardening required

Automated or manual publishing can proceed only when the configured publishing integration record has been successfully verified. The publishing service evaluates the invariant:

integration.is_enabled == true && integration.is_verified == true

If unverified or disabled, the dispatch transaction halts immediately with status PUBLISH_INTEGRATION_UNVERIFIED, preventing dispatches with faulty credentials.

WordPress Duplicate-Publishing & Idempotency Reconciliation Planned production-hardening requirement

A critical edge-case occurs when the application dispatches a publish request, WordPress creates the post, but the network connection drops or times out before DailyBlog AI receives the HTTP response:

  1. Application dispatches POST /wp-json/wp/v2/posts to the external WordPress site.
  2. WordPress successfully processes the post and allocates a remote post ID.
  3. Network drops or times out before the HTTP 201 response reaches the Celery worker.
  4. DailyBlog AI cannot immediately determine if the post was created or failed in transit.
  5. A naive blind retry would create a duplicate, publicly visible WordPress post.

Architectural Defense Strategy:

  • Publishing Attempt Identifier: Persist a unique publish_attempt_id (UUID) in blogs before initiating the network call.
  • External Post ID Tracking: Store the external WordPress post ID (wp_post_id) and canonical URL as soon as confirmation is acquired.
  • CMS Reconciliation Before Retry: Before executing any retry on an ambiguous failure, the worker queries the WordPress REST API by slug or title correlation to detect if the article was already created remotely.
  • Never Blindly Retry: If reconciliation discovers the post exists on WordPress, it marks the blog as PUBLISHED and attaches the remote post ID, avoiding duplicate creation.
  • Distinguishable Lifecycle States: The blog publishing lifecycle strictly distinguishes between: PUBLISHING, PUBLISHED, PUBLISH_FAILED, and PUBLISHING_UNKNOWN / RECONCILIATION_REQUIRED.
Failure Handling Protocol: If WordPress returns 401 Unauthorized, 500 Internal Error, or an unresolvable network timeout, the transaction marks the blog state as PUBLISH_FAILED, commits the diagnostic log, and generates alert notifications routed strictly to the Editor and Company Admin. The active blog cycle remains open and unresolved until manual resolution.

22. Redis & Celery Queue Architecture Architecture Decision

Redis serves as a high-speed cache and Celery task broker, strictly differentiated from PostgreSQL's durable persistence and LangGraph's workflow engine:

  • Redis Responsibilities: Asynchronous task broker for Celery, short-lived coordination state, active edit locks, and rate-limiting counters (OTP/CAPTCHA). Redis is not designated as a persistent result backend.
  • Celery Worker Responsibilities: Asynchronous, background, and scheduled job processing: specifically scheduled publishing dispatch, periodic cron polling via Celery Beat, background document ingestion where appropriate, and long-running background tasks. (Celery is an asynchronous worker system, not the AI reasoning engine).
  • LangGraph Workflow Responsibilities: AI workflow orchestration, topic ideation and selection, iterative research/retrieval flow, blog planning, draft generation, format and SEO validation flow, human-in-the-loop state checkpoints, and conversational state transitions. (LangGraph orchestrates graph state transitions but relies on PostgreSQL for durable persistence).
  • PostgreSQL Responsibilities: Durable, ACID-compliant system of record for all organizational entities, user credentials, publishing schedules, blogs, conversational thread checkpoints, and pgvector embeddings.
  • Worker Queue Segregation: Queues are partitioned into default, background_tasks, and publishing to ensure scheduled publishing dispatches are never starved or delayed by concurrent background operations.

23. n8n External Automation Boundary Architecture Decision

Strict Decoupling Mandate: n8n is strictly an external integration orchestrator (e.g. forwarding publication alerts to external Slack/Discord webhooks). n8n is NEVER the source of truth for blog lifecycle states, tenant ownership, memory, review approvals, or WordPress credentials. Core business state remains exclusively inside FastAPI + PostgreSQL + LangGraph.

25. Security & Credential Defense Architecture Decision

Credential Protection at Rest

  • User passwords hashed via bcrypt / argon2 with unique cryptographic salt.
  • Third-party publishing credentials (WordPress Application Passwords) are encrypted at rest using application-level Fernet symmetric encryption. The encryption key is supplied through protected environment configuration and is never hardcoded or returned through normal API responses.
  • Encryption keys injected via protected environment variables; never hardcoded or stored in Git.
  • Credentials scoped strictly to integration records; never returned in normal API responses or UI.

Edge Rate Limiting & Anti-Abuse

  • Strict rate limiting on OTP requests: max 3 attempts per corporate email within 24 hours.
  • CAPTCHA solve enforcement: max 3 failures before temporary cooldown; rate-limited challenge refresh.
  • Destructive account deletion requires explicit password re-authentication and double confirmation.
